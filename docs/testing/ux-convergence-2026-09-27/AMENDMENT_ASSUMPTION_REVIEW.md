## Production semantics checked

The assertions route is `app/api/dossiers/[dossierId]/evidence/assertions/route.ts`. It enforces same-origin mutation, ordinary dossier context/access and expected revision. Creation requires accepted, nonprovisional, nonretired source anchors; it sets new review fields to null and status to `needs_review`. Review is allowed only for a currently pending assertion. Supersession accepts only a currently accepted assertion and preserves its reviewed provenance and text. The route does not accept an in-place statement edit or a client-supplied reviewer. Existing migration guards also protect reviewed assertion identity/provenance.

The supported workflow consists of two separate writes—supersede old assertion, then create a new one. There is no explicit predecessor/replacement ID submitted or stored by this script. “Replacement” describes the intended QA workflow, not a new persistent lineage relationship or one atomic replacement transaction. If creation fails after supersession, the run must remain incomplete until that partial state is assessed; it cannot be labelled an all-or-nothing edit.

`app/dossier-security.ts` allows the **assertions** action to owner, contributor and reviewer. It denies viewers. Therefore this run proves the selected reviewer can accept and the viewer cannot; it does **not** prove assertion acceptance is reviewer-exclusive. The distinct **approve** permission is reviewer-only for governed outputs. The test and its conclusions must preserve that distinction.

All three assertion mutation paths call the existing `loadCurrentEvidenceOutputs`, `evidenceOutputStateStatements` and `evidenceOutputAuditInputs` helpers. Source inspection shows they append `PROFESSIONAL_ASSERTION_CHANGED` stale-state/audit entries for outputs currently marked current. In this fixture those arrays are empty. **Source presence is not execution evidence for output invalidation.** Existing output/approval tests can retain their earlier independent scope, but this run cannot be used to close their integrated journey.

`createDossierSnapshot` recomputes stored readiness before sealing. It excludes the expected report-generation circular prerequisites (`OUTPUT_REQUIRED`/approval-related reasons) and rejects the other blockers shown above. Thus the observed snapshot refusal is consistent with missing real prerequisites, not evidence that the new hypothetical assumption alone blocked sealing. Pending/replacement assertion status is not an independent generalized conclusion recalculation in this implementation; snapshot acceptance selection and output staleness remain separate contracts.
