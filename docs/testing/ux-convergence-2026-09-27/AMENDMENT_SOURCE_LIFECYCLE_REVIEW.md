### Local-session identity boundary

Its local path calls `getLocalSessionUser` afresh, which checks token hash, revocation, expiry, idle cutoff, active account and password-change time (`app/local-auth.ts:27–55`). No explicit Matter contract permitting that late local-session delivery was found in the inspected sources.

This is the same final private-read authorization boundary, not a claim of an additional observed exploit. The existing Studio history implementation supplies a concrete consistency precedent: `app/studio-report-history-server.ts:79–81` captures the exact local token hash and evaluates a live session predicate in the history queries; lines 103–109 check live authority again after the rows return.

If unavailable or changed, fail closed. Then call `requireDossierAccess` using the **original** organization-bound context, and compare the captured participant identity/role as above. `identityOnly` does not refresh organization selection or provision/select a replacement organization. Include a synthetic local-session revocation/identity-change regression rather than asserting this works solely from the membership test.

Trusted provider headers are the identity assertion on the accepted request; calling the same helper again cannot introspect a provider's later logout. Do not claim provider-side revocation of an already accepted request has been verified. The existing four byte-response guards already cover organization/participant loss, but not this separately identified local-session refresh; any shared helper adoption for those guards should be explicit and tested, rather than describing them as already session-fenced.

This is a concrete model/UI behavior to include in the unclosed replacement-source acceptance: the current document badge is not proof that its new bytes received a new explicit document-review event. No second P1 is asserted without deciding the intended logical-document versus per-version acceptance contract.
