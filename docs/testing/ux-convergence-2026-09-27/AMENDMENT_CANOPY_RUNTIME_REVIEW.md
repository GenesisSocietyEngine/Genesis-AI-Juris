## Source-supported explanation

- `tests/p1-organization-erp.test.ts:114` creates one Miniflare instance and D1/R2 bindings in `before`; `:176` disposes it in `after`. There is no SQLite subprocess per statement in this harness. Routes are bundled once by esbuild and called directly through the test transport (`:573`), while their database/object-store operations cross Miniflare's runtime boundary.
- `:613` awaits four scenario subtests sequentially. Each creates a distinct Matter, uploads nine original documents, creates and reviews source anchors, uploads scenario revisions, exercises proposal reject/edit/accept and resumability, runs and links the simulation, seals PDF/JSON outputs, checks independent approval and denied access, downloads those outputs and a presentation PDF, replays the recorded decisions through a fresh authoritative session, and reopens the Matter. `:675` then performs two further causal updates on Base, retaining and checking stale approved output bytes. This is deliberately much more work than one scenario outcome calculation.
- `app/canopy-workflow.ts:86`, `:148`, `:158` and `:223` show sequential per-source/per-anchor/per-proposal mutations. `:244` validates current authority/evidence through fresh reads and resume; `:291` generates a snapshot and both output formats. These are actual workflow operations, not only assertions. `tests/helpers/canopy-replay.ts:20` repeats the authoritative play-session sequence.
- Every governed request has several real database operations before its particular action. `app/dossier-server.ts:51` reads the actor, ensures the personal organization, and resolves organization authority. `app/organization-store.ts:40` performs an idempotent two-insert batch for that ensure, `:106` revalidates current membership before the joined Matter access read, and `:85` adds authority guard statements to mutation batches. Those security checks are not a suggested optimization target without preserving their race protections.
- Installed Miniflare is `5.20260911.0-alpha`. `node_modules/miniflare/dist/src/index.js:118497` returns a proxy for D1; `:103799` / `:103815` perform serialized sync/async calls across its local HTTP bridge. Its synchronous fetcher (`:103231`) reuses a worker thread and waits with `Atomics.wait` for a response. Thus many statement-building/binding/execution calls can incur harness transport/wait overhead even though Node calls the application route handler directly. This is evidence of a plausible overhead mechanism, not a measured attribution of the full elapsed time.

## Excluded explanations and limits

- No deliberate sleep, timing backoff, or artificial delay appears in the Canopy test, workflow or replay helper. Repeated idempotency checks are real repeated API calls, not timer retries.
- PBKDF2 (600,000 iterations) exists in password authentication, but the Canopy transport supplies the synthetic trusted identity header (`tests/p1-organization-erp.test.ts:79`). `app/chatgpt-auth.ts:21` returns that identity before local-session resolution. Password enrollment/login is exercised by separate earlier tests, not on each Canopy request. It does not explain the isolated Canopy scenario durations.
- This is a persistent workerd/D1/R2 harness, not repeated launches of a SQLite command adapter. Miniflare's synchronous bridge worker is also reused.
