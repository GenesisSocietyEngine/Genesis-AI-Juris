## Substep 1: conditional workspace saves

The intended outcome is that a stale Studio editor cannot replace another saved workspace, while its own consecutive autosaves can proceed in order. A conflict must retain editable inputs and export, require an explicit reopen/discard choice, and never fetch a fresh token to silently authorize stale edits.

The additive `ConditionalStudioDraftStore` exposes `readSnapshot` and `writeIfUnchanged`; the original three-method `StudioDraftStore` contract remains callable and custom memory/wrapper implementations continue to work. Application-support snapshots retain an exact-byte digest/absence token bound to the resolved target, detached workspace access and original valid UTF-8 JSON, including BOM. Formatting changes count as generation changes. Frozen conditional writes use the existing root coordinator and preservation guards; snapshots advance only after a successful commit.

`StudioWorkspaceSession` owns one editor's save chain. It freezes each draft/progress at submission, then uses the token from the loaded generation or its preceding successful own save. A permanent conflict/unsupported/recovery failure blocks queued and later writes. A transient error skips already submitted successors; a later retry keeps the same token. An unacknowledged committed write therefore produces a conflict rather than permission to replace newer data. Legacy custom stores retain their explicit unconditional semantics, with ordered frozen submissions; they do not acquire conditional guarantees merely by implementing the old interface.

The wizard uses this session for load/autosave/awaited save and fences asynchronous UI completion by storage epoch. A persistent live-region conflict card exposes frozen unsaved scenario export/clipboard and an explicit reopen dialog. “Keep editing” retains input and the blocked generation; “Reopen and discard” reloads intentionally. The conflict action is scrolled into view. Import refuses to start from an already blocked workspace session. Existing recovery failures remain read-only and existing awaited-save failures still prevent subsequent export/navigation success claims.

## Substep 1 boundary and remaining work at that checkpoint

This substep has **no aggregate journal**. The inherited sidecar-first/workspace-second import remains non-atomic. Mandatory recovery before either store, a root-matched service bundle, busy/frozen import adoption, immutable before/after intent, transaction-owned promotion/retired files and fault-boundary tests are subsequent reviewed steps. The root-owned application wrapper can forward the new conditional interface after its API is accepted; current custom wrappers retain their prior behavior.

The reviewed design selects coordination within the current main Dart isolate/process, retained staging/completed packages with no automatic cleanup, inert unpublished staging, and blocking both stores for invalid/future/conflicting published intent. Imported stale context/originals remain unchanged except the active saved revision; calculation is cleared, progress starts at Describe with no completed stages, and no automatic source rebinding/reconfirmation occurs.

The upcoming aggregate boundary will reject numeric tokens whose Dart decode/re-encode changes their exact decimal value. Whitespace/exponent spelling may change in a supported after-envelope; silent numeric value rounding is not accepted merely because the original is retained. Proposed limits approved for that later boundary are 4 MiB per payload, 64 KiB manifest, depth 64, 100,000 JSON nodes and 64 MiB/32 regular files per transaction package. Ordinary existing reads are not newly restricted by those import limits in this substep.

Actual Android/iOS process-death receipts, fresh native recomputation after aggregate recovery, cross-store conflict behavior, enlarged-text/spoken accessibility and physical devices remain open. No local widget or constructed disk-state test closes those application acceptance gates. No multi-process lock or power-loss durability is claimed.

## Substep 2: mandatory recovery gate and immutable import intent

Substep 1 was committed locally as `67f5d04`. This backend substep makes a published aggregate intent authoritative before either ordinary workspace or sidecar I/O can proceed. It is separately reviewed before the matched application services bundle and wizard import are connected. The existing workspace model and decoder move without changing their parsing policy; the old store import continues to re-export `StudioWorkspace`.

The shared root coordinator enters recovery once, without reentering either public store. Authoritative reads and writes from both stores use that gate; exports of already held snapshots or edits remain available. The internal import entry validates and freezes caller text before awaiting the directory provider, then checks both loaded snapshot targets and exact before hashes under the same resolved-root reservation. Its sealed completion receipt provides the exact committed snapshot identities without a fresh read that could silently authorize a concurrent editor.

Each retained package has immutable original, before/after payloads and a versioned manifest with exact hashes, byte counts, case identity and auxiliary-generation descriptors. Before absence is explicit. Unpublished `staging-*` remains inert; publishing is a same-parent rename to `pending-*`. Recovery validates the entire package, both domains, all auxiliary generations, the completion destination and conservative capacity for both promotions before changing a target. Promotion copies are verified; old targets move to transaction-owned retired paths. Partial promotion bytes are retained before rebuilding. Both targets must match the intended after bytes before the directory becomes `completed-*`, which remains retained and never replays.

Invalid, future, mismatched, non-regular, oversized or conflicting pending state blocks both stores with retained paths and bytes. A missing primary requires transaction-owned retirement proof unless its immutable before state was absent. A matching after primary is idempotent. The new aggregate boundary conservatively refuses unresolved/malformed auxiliary generations as well as future ones; ordinary per-file reads keep their existing compatible recovery policy. No `.bak`, `.tmp`, orphan generation or completed/staging package is automatically deleted.

The supported imported artifact preserves its complete source, stale fingerprint/context and legacy record. Only the active saved revision advances and calculation is cleared. Workspace progress restarts at Describe with no completed stages. Numeric spelling or whitespace in a supported after envelope may differ; numeric value must not. The bounded pre-decode scanner rejects rounded/non-finite numbers, duplicate decoded object keys and invalid caller UTF-16 before any encoding replacement. Escaped surrogate JSON strings remain supported. A leading BOM is retained in originals and committed byte identities; case IDs require exact UTF-8 identity while allowing a valid leading U+FEFF. Limits are 4 MiB per payload/retired/promotion file, 64 KiB manifest, depth 64, 100,000 nodes, 128 numeric-token characters and 64 MiB/32 files per package. These new-import/recovery limits do not narrow ordinary existing data reads.

## Substep 3: matched application services and frozen import adoption

The reviewed journal backend was committed locally as `c4f9e61185c36165dccc06e1d5683166ae316820`. This next substep connects aggregate import to the actual wizard through `StudioAuthoringServices.applicationSupport`. The factory constructs a conditional workspace and tax store from one provider; an optional `observeWorkspace` decorator must preserve the conditional interface. Both exact snapshot paths are still checked against the resolved root inside the commit lease. There is no constructor that silently combines unrelated stores. The default `JurisApp` bundle is retained across rebuilds. An explicitly injected legacy workspace keeps ordinary editing but cannot open an implicit tax store or perform an aggregate import.

Import captures clipboard text once, sets busy and removes keyboard focus before awaiting anything. Form fields are read-only, pointer actions and navigation are disabled, and the queued import follows only that editor's acknowledged autosaves. A sidecar snapshot is observed through the matched bundle; the workspace token is the session's existing token, never a fresh permission-granting read. The screen adopts Describe/empty progress, source and committed token only after verified completion and only for the same mounted storage epoch. Scenario-only import follows the same save-before-adoption rule. Rejected input retains the clipboard and current editor; a generation conflict preserves export and requires explicit reopen/discard. Published intent remains recoverable independently of widget lifetime.

The service preserves imported stale fingerprint/context and the whole legacy object, clears calculation and advances only the active saved revision. Root review found that incrementing `u64::MAX` would create an artifact Rust could not calculate; exhausted/out-of-range saved revisions now fail before staging, and the journal also rejects out-of-range immutable revisions. The new import guard applies to clipboard source-only imports too, preventing duplicate-key/numeric loss before that source is persisted; ordinary existing reads are unchanged.

The root-owned application harness now obtains both stores from this bundle. Its observation wrapper forwards `readSnapshot` and the exact `writeIfUnchanged` future as well as the legacy methods. This is an adaptation of the inherited two-phase harness; the separately developed six-phase harness and its runtime receipts are not implied by local analysis.
