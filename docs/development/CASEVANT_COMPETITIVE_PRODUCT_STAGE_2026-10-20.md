# Competitive product review and implementation instructions — 20 October 2026

## Decision and scope

Build CaseVant around a defensible decision package: the question, options, supporting passages, unresolved evidence, conditions, owner and next action. The intended initial users are lawyers/consultants and advisory teams handling complex decisions. This is a product positioning hypothesis, not validated demand or a claim of professional approval. Preserve the nine case categories, independent working copies, hypothetical scenarios and exact historical source identities.

This plan amends the priority order in the canonical product instructions and backlog. It does not cancel the [compatibility/authority acceptance work](CASEVANT_COMPATIBILITY_STAGE_2026-10-20.md). Delivered functionality must not be rebuilt merely to resemble a competitor. The first new slice fixes saved-case retrieval; later slices below require their own review, tests and Sites receipts.

## Detailed implementation contract: saved-case retrieval

1. Add optional `q` to the existing authenticated Studio catalogue GET. Search title, case identifier, numeric saved ID and already-displayed author name only; never email, document bodies or private grants. Keep the exact single-ID open/recovery branch unchanged. Filter within existing visibility and before the keyset page limit. No schema or source-template migration is required.
2. Accept at most120 input characters; trim and case-fold query letters, reject control characters and unpaired surrogates. Treat wildcard punctuation literally. SQLite ASCII `lower()` alone is insufficient for RU. D1 additionally limits LIKE/GLOB patterns to50 bytes: the first GLOB candidate failed real-handler Russian acceptance and was replaced. Use parameterized `instr` with ASCII lower and the fixed Russian-alphabet folding on title/displayed author; no untrusted SQL fragments. Prove behavior against migrated D1. A `#123` query selects exact saved ID within visibility; plain numbers remain substring queries. This is literal EN/RU substring search, not stemming, transliteration, tokenized AND search, accent folding or multi-character Unicode case expansion. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
3. Bind cursors to normalized query. Continue accepting the legacy two-field cursor for an empty query. A filtered cursor with another query, or a filtered cursor used without its query, returns400. Keyset order remains updatedAt DESC/id DESC. No total count or global title-order claim is introduced; local sort explicitly covers loaded results only. Evaluate indexed search separately if representative data shows unacceptable scan cost.
4. Use an explicit labelled Search form and Clear action, not a request on every keystroke. Results identify the submitted query. Replacing/clearing a query clears prior rows/cursor, cancels active reads and fences late callbacks. Refresh/pagination retain submitted query. Account authority changes synchronously hide results and cancel old reads. No query is written to case data or browser storage.
5. Test older-than-first25 retrieval; duplicate titles/timestamps; multiple filtered pages; punctuation `% _ * ? [ ]` and quotes; mixed-case EN/RU; author/IDs; no-match versus no-cases; maximum/invalid input; cursor mismatch; owner/shared/admin/private/foreign boundaries; grant revocation between pages; query reset/races; no writes. Preserve row links/version/privacy, loaded sort, language/org context and long-title/narrow layouts.
6. Review the diff and full user journey, then normal PR/main integration, exact merged-source CI and portable build, retained prior assets, archive-backed Sites save/deploy and both-origin asset checks. Record actual authenticated Chrome actions, screenshots/widths and limits under docs/testing. Use read-only existing authorized cases; never save/delete merely to test retrieval. Receipt must identify actual runtime, archive, saved version and native deployment. Do not publish a source-only success as a deployed release.

## Additional observed P2 refinement: return to search results

Production acceptance opens saved ERP20 correctly (196nodes/321connections, saved receipt) without mutation. Browser Back returns to My cases but resets the submitted query; Studio's own URL normalization also drops incoming organization/return_to hints. Establish the prior-runtime baseline before assigning a regression. After the retained authority/compatibility checks, make this a separate UX/navigation slice: preserve an account/organization-scoped in-memory origin context for query, loaded sort and results; offer a clear guarded return; discard stale context at identity/source transitions. Do not persist private search text across accounts, treat a Studio draft as a governed Matter, skip unsaved-work confirmation or rewrite existing cases. Acceptance: older result→exact saved editor→same search/result; cancellation=zero writes; stale account/source context is discarded; EN/RU/narrow/keyboard paths work. Reuse existing workspace/navigation guards rather than adding another router. This refinement is identified, not shipped in v151.

## Proposed measurements, not results

Baseline with at least5 consented evaluators: find a specified older saved copy and, in ERP, an authorization, evidence gap, owner and next action. Record correct retrieval/time, misinterpretation and source inspected. Proposed success: >=80% correct retrieval within30s per task, zero unauthorized results or lost work. Proposed concise report target: Base <=5 pages for a representative category cohort, with no omitted critical conditions/gaps; retain full export. These are hypotheses pending measurement, not present product performance. Gather before/after timings, dataset size and server query latency (proposed p95<1s for a representative10,000-row authorized metadata fixture). Do not collect client content or add telemetry without a defined consent/data policy.
