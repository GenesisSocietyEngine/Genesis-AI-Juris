# v59 First Four Case Types

v59 turns the Case Core and multi-view foundation into four complete,
package-driven professional workflows:

| Package | Test mode | Primary output |
| --- | --- | --- |
| Advisory decision | Evidence and option review | Decision memorandum |
| Tax & compliance | Source, compliance and economics comparison | Tax position memorandum |
| ERP incident & solution | Root-cause and acceptance-process verification | Solution design |
| Training simulation | Deterministic Rust route execution | Playable scenario |

The allowlisted `case-type-playbooks.v1.json` contract defines each package's
intake questions, AI focus, required record groups, canonical mobile thresholds,
test mode and output profiles. Web and Flutter consume byte-identical bytes and
pin every case to an immutable `caseTypeId@1.0.0`.

## Six-stage behavior

The Guided Studio shell remains stable while package data changes its content:

1. **Describe:** package-specific intake and intended result.
2. **AI draft:** a proposal constrained by the selected package.
3. **Facts:** package-specific evidence and governance requirements.
4. **Views:** the package's professional projections over one canonical case.
5. **Test:** review, compare, process or play mode.
6. **Finish:** the package's primary and supporting output profiles.

Advisory, tax/compliance and ERP matters are not forced into a pretend game
tree. Their Step 5 evaluates structured completeness and review controls. Only
the training package must compile and play a route. On mobile, every package
still passes its exact canonical `ScenarioDefinition` through Rust schema
validation; only training then invokes Rust runtime execution.

Tax/compliance remains fail-closed until the matter supplies a legal as-of date,
authoritative HTTPS sources and the lawful-planning compliance gate. The mobile
canonical fact record carries the equivalent dated source and reporting-duty
evidence.

## Guardrails

- packages are immutable allowlisted data, never executable plug-ins;
- AI proposes structured changes and cannot approve or silently mutate a case;
- one canonical case remains the source for every view and report;
- Rust remains the authoritative native validation and execution boundary;
- legacy fingerprints, canonical bundle bytes and all 18 parity routes remain
  unchanged;
- release requires exact-SHA Rust, Flutter, Android and iOS evidence plus
  byte-identical web/mobile playbooks.

The resulting product promise is: turn an unstructured professional matter
into a versioned, explainable, testable and reusable decision package.
